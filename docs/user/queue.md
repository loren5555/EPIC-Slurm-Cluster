# 排队与优先级

GPU 主机的任务需要通过 Slurm 排队。任务提交后，Slurm 会根据资源是否空闲、任务申请的资源大小、等待时间以及用户和 Account 的近期使用情况安排运行顺序。

## 怎样提交更容易排到

### 1. 只申请实际需要的资源

提交任务前先估算程序需要的 CPU、内存和 GPU 数量：

- 不需要 GPU 的任务不要填写 `--gres=gpu:N`；
- CPU 数量按程序实际并行度填写，不要申请整台主机（目前CPU还未设限）；
- 内存按峰值需求估算，并给出合理余量（目前内存还未设限）；
- 多卡任务只在程序确实需要时申请多张 GPU。

申请的资源越多，能够同时满足条件的空闲资源越少，任务通常越难找到合适的运行时机。申请过大的资源也会让其他任务无法使用剩余资源。

### 2. 估算真实运行时间

`--time` 是任务允许运行的最长时间，不是程序一定会运行的时间。请根据小规模测试估算，并设置一个覆盖正常波动的时限：

```bash
# 例如：预计运行 2 小时，预留到 3 小时
#SBATCH --time=03:00:00
```

不要把所有任务都设置成最大时长。较短且合理的时间限制能让 Slurm 更容易进行 backfill，在不影响已经排队任务的情况下提前安排短任务。

如果不确定运行时间，可以先用较小数据集提交测试任务，使用 `sacct` 查看实际耗时：

```bash
sacct -j <job-id> --format=JobID,State,Elapsed,AllocTRES
```

根据测试结果调整正式任务的 CPU、内存、GPU 和 `--time`，不要直接用测试任务的过大申请值运行完整实验。

## 哪些因素会影响顺序

Slurm 的多因素优先级会综合考虑：

- **Fair-share**：近期使用较少的用户和 Account 通常拥有更有利的份额；
- **等待时间**：任务等待越久，等待时间因素会逐步增加；
- **Job QoS**：管理员授予的 QoS 可能改变排队优先级；
- **资源和分区条件**：只有满足目标分区、CPU、内存和 GPU 条件时，任务才能运行。

Fair-share 影响的是排队顺序，不是累计用量配额。正常任务不会因为过去使用过资源就被禁止提交，也不会因为另一个任务优先级更高而被抢占。符合资源条件的短任务可能先运行，但长时间等待的任务会逐步获得等待时间加成。

### 资源如何计入 Fair-share

作业运行时，申请到的 CPU、完整 GPU 和 GPU shard 会按照以下权重折算为
billing resource，并随运行时间累计到 Fair-share 使用量中：


| 资源           |       A100 分区 |  RTX 4070 分区 |
| ---------------- | ----------------: | ---------------: |
| 1 个 CPU core  |            0.05 |           0.05 |
| 1 张完整 GPU   |               1 |              1 |
| 1 个 GPU shard | 0.25（1/4 GPU） | 0.5（1/2 GPU） |

例如，一个任务在 A100 分区申请 4 个 CPU core 和 1 张完整 GPU，其资源权重为
`4 × 0.05 + 1 = 1.2`。相同运行时间下，申请资源越多，累计的 Fair-share
使用量越高。

这些数字是集群内部的资源计费权重，不是费用，也不会独立决定任务何时开始。
实际排队顺序仍会综合资源是否可用、等待时间、近期使用量和 Job QoS 等因素。

可以使用以下命令查看自己的任务和优先级组成：

```bash
squeue -u "$USER"
sprio -j <job-id>
```

如果任务处于 `PENDING`，先查看等待原因：

```bash
scontrol show job <job-id>
```

## 提交任务前的检查清单

1. 是否真的需要 GPU？需要几张？
2. CPU 和内存是否与程序规模匹配？
3. 是否用短测试任务测过运行时间？
4. `--time` 是否覆盖正常运行时间，但没有随意设置成最大值？
5. 输出目录和日志路径是否已经准备好？
6. 是否可以把一个大任务拆成预处理、训练、评测几个阶段？

鼓励先小规模验证，再提交正式任务。合理的资源和时间申请通常比反复取消、重新提交或长期占用 Interactive App 更容易排队，也更方便其他用户共享集群资源。
